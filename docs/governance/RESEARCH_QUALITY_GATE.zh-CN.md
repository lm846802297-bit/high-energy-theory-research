# 共享科研质量门

**状态：** 已采用的共享最低标准  
**生效日期：** 2026-11-23  
**适用范围：** 采用中央规范体系的研究变更

科研质量门将共享科研要求映射到与任务类型相适应的证据。它不是固定的数学工作流，不规定统一数值容差，也不要求每项任务机械执行所有测试。

## 1. 十项质量要求

| # | 质量门 | 最低证据要求 |
|---:|---|---|
| 1 | 精确源码与基线身份 | 仓库、分支、完整基线/源码 commit SHA；相关文件/blob 身份；必要时记录工作树状态 |
| 2 | 输入来源与完整性 | 来源/版本/许可或访问条件、精确输入身份和变换过程；字节可用时记录 SHA-256，无法归档字节时提供不可变版本定位符 |
| 3 | 执行环境 | 实际执行目标、操作系统/运行时、编译器/解释器、依赖、命令和相关资源信息（仅适用于实际执行代码的任务） |
| 4 | 硬件与物理/数值配置 | 相关 CPU/GPU/内存/存储信息，以及物理参数、单位、约定、网格、精度、容差、随机种子和边界条件；没有相应执行时标记 N/A |
| 5 | 原生输出与归档完整性 | 可编辑源码/推导、原生数据/结果、日志/报告、输出清单、计数/单位、哈希及经核验的远端归档位置 |
| 6 | 数值精度、收敛与误差 | 数值方法、精度、网格/求积/插值/积分检查、不确定度/误差估计、实际残差，以及预先定义的验收标准 |
| 7 | 独立科学/物理验证 | 解析极限、量纲、守恒/对称恒等式、独立推导/实现、原始文献/表格比较或适用于具体主张的领域验证 |
| 8 | 相关软件回归测试 | 覆盖变更代码/Schema/工作流行为的测试、精确命令和结果；可在主执行环境或批准的验证环境运行，Actions 为可选 |
| 9 | 独立技术审查 | 由作者实现过程之外的审查者检查实际 diff 和证据；记录发现、严重程度、处理结果和审查的 commit SHA |
| 10 | PR 审查与集成 | 聚焦 PR、准确的范围/状态、合并前审查和负责人授权；合并后验证 merge commit 及规范分支状态 |

## 2. 任务类型

按以下任务类型选择要求。项目可以增加更严格的领域规范，但不得削弱共享最低要求。

| 任务类型 | 必需质量门 | 常见 N/A 项 |
|---|---|---|
| 解析推导/理论 | 1、2、4、5、7、9、10；使用符号/代码执行时还需 3、8 | 纯手工推导的 3；没有数值主张时的 6 |
| 数值计算/模拟/扫描 | 1–7；第 8 项仅在变更或新增代码/工作流时适用；第 9、10 项在采用 PR 审查与集成时适用 | 不涉及实际代码执行时的 3、4；其他确实不适用的单项检查须说明原因 |
| 代码/校验器/工作流变更 | 1、2、3、5、8、9、10；影响物理/数值行为时还需 4、6、7 | 不影响科学行为的纯机械工具变更可将 6 或 7 标记 N/A |
| 数据变换/归档迁移 | 1–5；工具变化时需 8；还需 9、10；数据含义/物理解释变化时需 6、7 | 保持字节不变的纯路径迁移可将 6、7 标记 N/A |
| 论文/文档/文献审查 | 1、2、5、7、9、10；使用编译/提取/脚本时还需 3、8 | 不产生新物理/数值主张或计算时的 4、6 |
| 仓库维护 | 1、5；适用时需 8；还需 9、10 | 不涉及输入、执行或科学内容时的 2–4、6、7 |

N/A 必须说明原因。适用但未执行的检查不得标记 PASS。

## 3. 质量门状态

每项适用要求使用以下状态之一：

- **PASS：** 对应证据存在，并满足针对精确范围和 commit 的验收标准。
- **FAIL：** 已执行检查或审查发现具体验收失败。
- **BLOCKED：** 因具体来源、资源、权限或依赖不可用，无法执行必需检查。
- **NOT RUN：** 检查适用，但尚未执行。
- **N/A：** 检查确实不属于任务范围，并说明原因。

不得从计划、源码存在、无关 CI 通过、进程正常退出、校验和一致或旧 commit 的结果推断 PASS。证据不充分时，按实际情况标记 BLOCKED 或 NOT RUN，不要强行判为 PASS。

## 4. 最小充分验收原则

验收以具体研究问题和拟支持的物理主张为中心，而不是以检查项目数量为目标。每项任务开始前，应尽可能明确：研究问题、工作范围、任务类型、预期影响的论文图表/公式/数值结论/物理判断，以及足以支持该主张的验收标准。

1. **明确研究目的。** 说明本任务可能改变哪一张图、哪一个公式、哪一个数值结论或哪一个物理判断。若无法说明与研究目标的关系，不应仅为扩大技术覆盖而启动任务。
2. **确定必要检查。** 从十项质量要求中选择直接影响本任务主张的检查。任务类型表给出适用性起点，不构成对所有测试、所有数值网格或所有工作流的机械执行清单。对不适用项标记 N/A 并说明理由；对适用但未执行项如实标记 NOT RUN 或 BLOCKED。
3. **复用历史验证。** 若源码、输入、约定、运行环境和被支持的主张均未发生相关变化，且历史证据可定位到精确版本，则直接引用既有验证，不重复计算或重跑。若其中任一相关依赖变化，只针对受影响的结果和检查进行复核；不得把无关变化当作全面重验的理由。
4. **一次性验收并冻结。** 在执行前定义数值方法、误差/容差和物理验收条件。达到预定标准后冻结该任务结果；除非出现具体错误、新证据、依赖变化或范围变化，不得在结束阶段追加条件或反复打开已通过项目。
5. **合并与归档。** PR 只要求完成其变更范围所必需的证据、审查和负责人授权。与当前 PR 及其所支持主张无关的后续工作，应记录为独立待办，不阻塞当前合并。合并后核实精确 merge commit 和规范分支状态。

补充执行规则：

- 数值方法和容差由物理问题与可观测量决定；中央规范不规定统一求积阶数、精度或百分比容差。
- 软件测试只验证它实际覆盖的代码路径或断言，不自动验证物理推导；数值收敛检查只验证测试设置下的数值稳定性，本身不验证模型或近似。
- 独立验证必须说明独立性；共享同一代数内核的两个封装程序不自动构成独立实现。
- 保留历史输出；假设、约定或代码变化时创建新版本结果，不覆盖旧结果。
- 不得为了清空检查台账、追求更高 CI 数量或完善通用平台而扩大当前研究范围。

## 5. 独立审查与 GPT 审查

审查者必须检查实际 diff、相关源码/输入溯源、测试覆盖、物理主张和验收证据，而不只是 PR 描述。

项目负责人可以指定 GPT 作为默认技术审查者。审查记录应注明审查的 HEAD SHA、审查范围、发现和处理结论。审查应独立于实现过程；若同一 Agent 同时负责实现和审查，应明确说明，并在可行时采用新一轮独立审查或其他独立检查。

技术审查评论不等于 GitHub 正式 APPROVE。不得冒充其他 GitHub 账户，也不得声称 GitHub 没有记录的批准。分支保护和平台权限由各仓库实际配置决定；本规范不默认要求额外的人类审查者。

## 6. CI 与合并

除非任务负责人明确要求特定工作流，否则 GitHub Actions 为可选。相关检查可以在主执行环境或批准的独立环境运行。只要能在其他环境取得必需证据，Actions 排队或不可用本身不阻止工作。

合并遵循 [Git 合并规范](GIT_MERGE_POLICY.md)。合并前必须完成 PR 审查、适用的必需质量门和负责人授权；N/A 项应按任务类型说明。若任务验收要求的证据尚未执行，不得合并。第 10 项质量门只有在合并后验证规范分支状态后才完全 PASS。

## 7. 与结构化结果状态的关系

数值运行使用 RCRPS v1.0.1 记录机器可读的执行、验证、科学成熟度和归档状态。质量门状态描述要求级验收，不替代 RCRPS 记录状态。
