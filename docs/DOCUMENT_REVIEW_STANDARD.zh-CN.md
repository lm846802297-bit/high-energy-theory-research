# 科研文档审查规范

**状态：** 已采用的共享规范  
**生效日期：** 2026-11-23  
**适用范围：** 采用中央科研规范体系的仓库中的实质性文档审查、编辑、迁移、归档分类和跨文档一致性检查。

本规范定义如何审查科研领域的可读文档。它补充[科研质量门](governance/RESEARCH_QUALITY_GATE.zh-CN.md)，不替代科学推导、数值验证或项目专属审查。

## 1. 按任务规模确定审查范围

对于实质性编辑，应审查文档中受到实质影响的部分。若任务声称完成全文审查、改变文档的科学权威性或生命周期，或迁移/归档文档，则应审查全文。

简单的拼写、标点或格式修正可以采用针对性检查。如果文档含义、证据和权威性没有变化，不要求重新进行完整的科学审查。

批量文件清单不等于内容审查。若任务声称完成逐文档审查，则每份范围内的文档都必须有独立审查结论。不能因为检查了某个目录或登记表，就推断其中未实际阅读的文件已经通过审查。

## 2. 审查维度

对每份范围内的文档，按适用情况检查：

1. **身份与角色：** 标题、目的、目标读者、项目/工作流以及文档类型。
2. **权威性与生命周期：** 当前权威文件、工作草稿、历史快照、已被替代的记录、生成文件或交付物。存在规范替代文件时，应明确指出。
3. **科学内容：** 公式、定义、约定、量纲、单位、近似、参数、极限，以及结论是否确实由引用的推导或数据支持。
4. **证据与引用：** 引用能够访问且确实支持相应主张。区分文献陈述、采用的假设、数值观察和科学结论。
5. **一致性：** 对照当前权威研究记录，核对模型假设、benchmark、数值、符号和状态描述。
6. **可复现性：** 在相关时记录源码版本、输入来源、配置、命令、软件环境、输出位置、校验和及验收标准。
7. **链接与资源：** 检查相对 Markdown 链接、锚点、图片、PDF、数据路径、脚本和跨文档引用。
8. **语言与结构：** 标题、范围、定义、论证、结果、适用条件和下一步应清楚。清理过时或相互矛盾的指令时，不得抹去有历史价值的事实。
9. **处置结论：** 保留、修订、标记为历史/已被替代、合并到规范文件、迁移或建议删除。删除前必须检查来源和入站引用。

正式审查记录中，不适用的项目应标记为 N/A。不能仅因为文档可读或格式整齐，就声称已经完成科学审查。

## 3. 审查结论与文档生命周期必须分开

在维护逐文档审查登记表时，使用以下审查结论：

- **PASS：** 所有适用检查均已完成，未发现需要处理的问题。
- **PASS_WITH_NOTES：** 在已审查范围内可以使用；已记录非阻塞性发现。
- **REVISION_REQUIRED：** 仍存在至少一项需要处理的内容、证据、一致性或表达问题。
- **BLOCKED：** 因特定来源、数据集、权限或必要上下文不可用，无法完成审查。
- **PENDING：** 仅完成文件清点，尚未进行内容审查。

文档生命周期/权威性应单独记录，例如：当前权威文件、工作草稿、历史文件、已被替代、生成文件、归档文件或疑似重复文件。**HISTORICAL 是生命周期分类，不是审查结论。** 历史文档仍可能有格式问题；PASS 也不会使旧文档自动成为当前权威文件。

## 4. 科学主张完整性

文档审查必须保留会影响主张含义的区别：

- 解析推导与数值实现；
- 单点一致与全局收敛；
- 软件/CI 通过与数值或物理验证；
- 条件性 benchmark 与一般性结果或最终排除；
- 项目采用的模型假设与独立确立的物理事实；
- 局部或部分计算与完整可观测量/物理过程。

编辑整理过程中不得静默改变结果、不确定度、benchmark、模型假设、适用条件或物理结论。若无法根据引用证据解决科学差异，应记录差异并交由独立决策处理。

## 5. 审查记录

当任务要求正式文档审计或迁移登记表时，至少记录：

- 仓库和精确审查 commit SHA；
- 文件路径、标题、角色、项目/工作流及生命周期/权威性；
- 审查结论；
- 发现的问题和所需操作；
- 审查者与审查日期；
- 相关来源、证据或替代文档链接。

对于代码、数据、Schema 和生成的数值产物，应使用相应的技术验证流程。不能把文档审查结论当成脚本、数据集或科学计算正确的证明。

## 6. 迁移、归档与删除

移动、合并、归档或删除文档前：

1. 确认文档角色、权威性、生命周期和独有科学内容。
2. 搜索所有入站引用，包括 Markdown 链接、代码导入、工作流路径、LaTeX 输入、脚本、清单和外部交接说明。
3. 保留旧路径到新路径的映射，并尽可能在同一变更中更新引用。
4. 对具有溯源价值的历史文件保留原始字节和指纹。如果审查登记表同时记录历史审查版本和当前文件，应使用不同字段分别保存；不得仅为了与当前 Git 树一致而覆盖历史指纹。
5. 集成后在规范分支上验证文件和链接。

不能仅凭标题或措辞相似就认定两份文档重复。合并前必须确认其科学命题、假设、证据、适用范围和文档角色确实等价。

## 7. 批量审查的覆盖率管理

进行完整的仓库文档审计时：

- 在统计前定义文件范围、文件类型和基线 commit；
- 建立路径唯一的文件清单，每份文档有独立审查结论；
- 区分文件清点覆盖率与实际完成的内容审查；
- 当需要保留历史指纹时，分别记录审查时的 commit/blob 身份和当前 Git 树身份；
- 文件新增、改名、迁移或删除时更新清单；
- 保留带日期的审查快照，避免后续变化改写历史审查记录。

只有声明的审查范围、文件清单、逐文档结论和路径/链接检查均相互一致，批量审查才算完成。本要求只适用于声称进行批量审查的任务，不意味着普通科研工作必须进行全仓库审查。
