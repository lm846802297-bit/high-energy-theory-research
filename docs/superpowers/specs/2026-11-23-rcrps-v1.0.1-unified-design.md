# RCRPS v1.0.1 Unified Source-Control Provenance Design

**Status:** Draft design for owner review  
**Design date:** 2026-11-23  
**Canonical repository:** `lm846802297-bit/high-energy-theory-research`  
**Baseline:** `b713bfdc971d1118406f619fe3a3fb5c9614e2a7`  
**Related proposals:** PR #28 (`source.revision_context`) and PR #29 (`execution.source_control`)  
**Decision approved in conversation:** every new v1.0.1 `run_manifest` must include `execution.source_control`, including non-PR runs; PR-specific fields must be explicitly `null` for non-PR runs.

## 1. Intent

Publish one backward-compatible RCRPS v1.0.1 source-control provenance contract that unambiguously records which Git revision was actually checked out and executed, how that checkout relates to a pull request (when applicable), and which workflow execution produced the record.

The contract must work for GitHub pull-request, push, manually dispatched, scheduled, workflow-run, merge-queue, and local executions. It must not force PR-only metadata onto non-PR runs or allow missing source-control context to pass for new v1.0.1 run manifests.

## 2. Goals

1. Require `execution.source_control` on every v1.0.1 `run_manifest`.
2. Keep `source.commit_sha` as the single canonical SHA for the exact commit checked out and used by the run.
3. Distinguish PR source-head SHA, target-base SHA, and a synthetic merge SHA actually checked out and tested.
4. Explicitly distinguish PR merge checkout from PR head checkout.
5. Require all PR-specific fields to be present and explicitly null for non-PR executions.
6. Retain workflow run ID and attempt metadata when a workflow execution exists.
7. Record checkout ref and working-tree state without claiming that dirty workspaces are fully reproducible from a commit SHA alone.
8. Preserve existing v1.0.0 records and the v1.0.0 schema byte-for-byte.
9. Keep the structured result profile separate from candidate Schema v1.4.3.7.
10. Make the validator enforce cross-field semantics, not merely JSON types and SHA string lengths.

## 3. Non-goals

- Do not rewrite, migrate, or backfill existing v1.0.0 manifests.
- Do not change the physical-result or validation-report semantics.
- Do not use source-control metadata as evidence of numerical convergence or physical correctness.
- Do not make GitHub Actions a mandatory research or merge gate; the existing compute and archival policies remain authoritative.
- Do not promote Schema v1.4.3.7 or its candidate FingerprintInputs contract.
- Do not merge PR #28 and PR #29 as competing standards.
- Do not introduce a duplicate `checked_out_sha` field when `source.commit_sha` already records the actual checked-out commit.

## 4. Approaches considered

### A. Adopt PR #28's `source.revision_context` layout

Advantages:
- distinguishes checked-out commit from PR head/base/tested merge;
- includes checkout mode and branch-ref semantics;
- includes working-tree state and dirty paths;
- has explicit semantic validation for merge and head checkout.

Trade-offs:
- moves execution provenance under `source`, mixing source-code identity with runtime event context;
- duplicates `source.commit_sha` with `checked_out_sha`;
- its current PR branch is stacked on an old base and its checks are not the canonical release evidence.

### B. Adopt PR #29's `execution.source_control` layout unchanged

Advantages:
- keeps execution event metadata under `execution`;
- includes PR URL/number, PR head/base/tested-merge SHA, workflow run ID, and attempt;
- current PR head has successful schema and structured-result workflow runs.

Trade-offs:
- the current schema makes `source_control` optional for run manifests;
- local/non-PR records can omit the object rather than explicitly recording null PR fields;
- it does not fully distinguish merge checkout from PR-head checkout;
- it does not enforce the equality between the tested merge SHA and the actual checked-out commit.

### C. Unified contract: PR #29 placement plus PR #28 checkout semantics

**Selected approach.**

Keep `execution.source_control` as the location for event and workflow provenance. Retain `source.commit_sha` as the canonical actual-checkout SHA; do not duplicate it. Add the checkout mode/ref and branch-ref semantics needed to distinguish PR merge and PR-head checkouts. Require the object for every v1.0.1 run manifest and require explicit nulls for PR-specific fields on non-PR runs.

This combines the clearest object placement and workflow metadata from PR #29 with the cross-field checkout semantics from PR #28, while simplifying the duplicate checked-out-SHA representation.

## 5. Versioning and compatibility

### 5.1 Existing v1.0.0

- `docs/schemas/research-result-record-v1.0.0.schema.json` remains byte-for-byte unchanged.
- Existing v1.0.0 manifests remain valid under the v1.0.0 schema.
- No historical record is rewritten or backfilled.
- The v1.0.0 validator behavior remains available through explicit schema selection.

### 5.2 New v1.0.1 schema

Create `docs/schemas/research-result-record-v1.0.1.schema.json`.

The v1.0.1 schema is a backward-compatible validation superset:
- it accepts v1.0.0 records under their existing v1.0.0 field requirements;
- it accepts v1.0.1 records;
- for a `run_manifest` with `schema_version="1.0.1"`, it requires `execution.source_control`;
- for a v1.0.0 `run_manifest`, it does not require `source_control`;
- `result_summary` and `validation_report` retain their existing field semantics; their v1.0.1 version labels do not acquire source-control fields.

The v1.0.1 validator should default to the v1.0.1 schema, which accepts both versions. The caller may still select the v1.0.0 schema explicitly.

## 6. Canonical field contract

Add the following required object to `execution` in a v1.0.1 `run_manifest`:

```json
{
  "source_control": {
    "event": "pull_request",
    "checkout_mode": "pull_request_merge",
    "checkout_ref": "refs/pull/104/merge",
    "pr_number": 104,
    "pr_url": "https://github.com/example/research/pull/104",
    "pr_head_sha": "<40-character PR head SHA>",
    "base_sha": "<40-character target base SHA>",
    "tested_merge_sha": "<40-character checked-out merge SHA>",
    "head_ref": "feature/example",
    "base_ref": "main",
    "workflow_run_id": 123456,
    "workflow_run_attempt": 1,
    "working_tree_state": "clean",
    "dirty_paths": []
  }
}
```

All keys in this object are required in v1.0.1. Values that do not apply or cannot be established must be represented explicitly as `null` where the property permits null; do not omit the property or fabricate a value.

### 6.1 Field definitions

| Field | Type | Meaning |
|---|---|---|
| `event` | non-empty string | Exact execution event name; examples include `pull_request`, `pull_request_target`, `push`, `workflow_dispatch`, `schedule`, `workflow_run`, `merge_group`, and `local` |
| `checkout_mode` | enum | `pull_request_merge`, `pull_request_head`, `branch_commit`, `detached_commit`, or `unknown` |
| `checkout_ref` | string or null | Exact Git ref checked out, when known; null for detached or unavailable refs |
| `pr_number` | positive integer or null | Pull-request number |
| `pr_url` | URI or null | Canonical pull-request URL |
| `pr_head_sha` | 40-character SHA or null | Exact source-branch HEAD for the PR execution |
| `base_sha` | 40-character SHA or null | Exact target-branch base revision associated with the PR execution |
| `tested_merge_sha` | 40-character SHA or null | Synthetic PR merge commit only when that commit was actually checked out and tested |
| `head_ref` | non-empty string or null | Actual PR source branch/ref name, not the synthetic merge ref |
| `base_ref` | non-empty string or null | Actual PR target branch/ref name |
| `workflow_run_id` | string, integer, or null | Workflow execution identifier, when present |
| `workflow_run_attempt` | positive integer or null | Workflow run attempt, when present |
| `working_tree_state` | enum | `clean`, `dirty`, or `unknown` |
| `dirty_paths` | array of strings | Repository-relative paths reported as modified/untracked; empty for a clean tree |

The exact checked-out commit remains `source.commit_sha`. No second `checked_out_sha` field is added.

### 6.2 PR event invariants

PR events are `pull_request` and `pull_request_target`.

For either PR event:
- `pr_number`, `pr_url`, `pr_head_sha`, `base_sha`, `head_ref`, and `base_ref` must be non-null and valid.
- The `tested_merge_sha` property must exist, but its value depends on `checkout_mode`.
- `source.branch` must equal `head_ref`; it identifies the contributor's source branch, not a synthetic ref such as `104/merge`.
- `source.commit_sha` always identifies the exact commit actually checked out and executed.
- `checkout_ref` records the actual checkout ref when known; it must not be substituted for `head_ref` or `base_ref`.

Checkout-specific rules:

1. **`pull_request_merge`:**
   - `tested_merge_sha` must be non-null.
   - `tested_merge_sha` must equal `source.commit_sha`.
2. **`pull_request_head`:**
   - `tested_merge_sha` must be null.
   - `source.commit_sha` must equal `pr_head_sha`.
3. **`unknown`:**
   - `tested_merge_sha` must be null.
   - `source.commit_sha` still records the exact checkout commit; the manifest must not claim it was a tested merge without evidence.

A PR event cannot use `branch_commit` or `detached_commit` as its checkout mode. If the runner cannot determine whether it checked out the merge or head, use `unknown` rather than guessing.

### 6.3 Non-PR event invariants

For every event other than `pull_request` and `pull_request_target`:
- `pr_number`, `pr_url`, `pr_head_sha`, `base_sha`, `tested_merge_sha`, `head_ref`, and `base_ref` must all be explicitly `null`.
- `checkout_mode` must not be `pull_request_merge` or `pull_request_head`.
- `source.commit_sha` continues to identify the actual checked-out commit.
- `checkout_ref` records the actual branch/ref if known; use null for detached or unknown checkouts.
- `event` records the actual event name; for a direct local execution use `local`.

This rule makes non-PR source-control context explicit and prevents placeholder or fabricated PR metadata.

### 6.4 Workflow-run metadata invariants

- `workflow_run_id` and `workflow_run_attempt` must either both be null or both be present.
- `workflow_run_attempt` must be a positive integer.
- Local executions without a workflow use null for both fields.
- Workflow metadata does not replace the Git source revision fields.

### 6.5 Working-tree invariants

- `working_tree_state="clean"` requires `dirty_paths=[]`.
- `working_tree_state="dirty"` requires at least one path in `dirty_paths`.
- `working_tree_state="unknown"` records that the state or path inventory could not be established.
- Paths must be repository-relative, normalized, unique, and free of absolute paths or parent-directory traversal.
- A dirty working tree is not made fully reproducible by recording only its base commit and dirty path names. If dirty source files affect the run, their exact contents or a reproducible patch/snapshot must also be archived and fingerprinted under the project's result-artifact policy. The manifest must not label a dirty run as clean.

## 7. Semantic validation requirements

JSON Schema validates required fields, types, formats, SHA lengths, and basic conditional requirements. The Python validator must additionally enforce:

1. `source.commit_sha` is the actual checkout SHA and is valid as a 40-character Git SHA.
2. PR event detection and PR/non-PR null semantics.
3. `source.branch == head_ref` for PR events.
4. Merge checkout equality: `tested_merge_sha == source.commit_sha`.
5. PR-head checkout equality: `source.commit_sha == pr_head_sha` and `tested_merge_sha is null`.
6. Unknown PR checkout does not claim a tested merge.
7. PR checkout modes are rejected for non-PR events; non-PR modes are rejected for PR events.
8. Workflow run ID/attempt null-pair semantics.
9. Working-tree state/path consistency and safe normalized paths.
10. v1.0.0 manifests are unaffected by v1.0.1 semantic checks.

A schema-valid record that violates a cross-field invariant must fail validation.

## 8. Test requirements

The v1.0.1 regression suite must include positive and negative cases for:

- v1.0.0 run manifest accepted by the v1.0.1 schema without source_control;
- v1.0.1 run manifest rejected when source_control is missing;
- v1.0.1 non-PR local, push, and workflow-dispatch records with all PR fields explicitly null;
- non-PR record rejected when any PR-specific field is non-null;
- PR merge checkout accepted only when tested_merge_sha equals source.commit_sha;
- PR-head checkout accepted only when source.commit_sha equals pr_head_sha and tested_merge_sha is null;
- unknown PR checkout accepted without claiming a tested merge;
- malformed PR SHA, URL, number, or branch-ref values rejected;
- source.branch mismatch with head_ref rejected;
- PR event with non-PR checkout mode rejected;
- non-PR event with PR checkout mode rejected;
- workflow ID/attempt mismatch rejected;
- clean/dirty/unknown working-tree cases and invalid dirty paths;
- v1.0.0 schema file remains byte-identical.

Existing strict JSON, input provenance, output integrity, CSV, and validator regression tests must continue to pass.

## 9. Documentation and migration

Update the English and Chinese RCRPS standard documents with identical field semantics and examples. Explain:
- v1.0.0 remains valid and unchanged;
- v1.0.1 run manifests always require source_control;
- PR-specific fields are explicitly null for non-PR events;
- the distinction between PR head, base, tested merge, and actual checkout;
- dirty working-tree limitations;
- explicit schema/validator selection and reproduction commands.

Update the archival policy and AGENTS.md references only after the v1.0.1 schema/validator contract is approved. New runs use the adopted v1.0.1 profile after its merge; historical v1.0.0 runs remain valid under v1.0.0.

Do not modify historical result manifests, calculations, input data, or scientific benchmarks.

## 10. Release and governance gates

The unified v1.0.1 implementation is ready for review only after:
1. the schema validates against Draft 2020-12;
2. all v1.0.0 compatibility tests pass;
3. all v1.0.1 schema and semantic regression tests pass;
4. the validator's existing input/output/CSV integrity tests pass;
5. English and Chinese documentation semantics match;
6. CI results, if available, are recorded against the exact PR head;
7. independent code review is complete;
8. the PR diff confirms v1.0.0 schema and historical records are unchanged.

The existing repository policy remains in force: Actions is optional supporting infrastructure and is not the sole research or merge gate. The final merge requires PR review and uses a merge commit.
