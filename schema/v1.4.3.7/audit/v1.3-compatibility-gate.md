# Historical Schema v1.3 compatibility gate

**Status: BLOCKED / UNVERIFIED.** Schema v1.4.3.7 remains an unreleased candidate.

## Evidence currently available

The latest static implementation review is recorded in [static-schema-migration-review-2026-10-23.md](static-schema-migration-review-2026-10-23.md). It documents implementation changes and unresolved gates; no tests or CI were executed for that review.

- The migration implementation in tools/migrate_v1_3_to_v1_4.py is a source-aware staging prototype using rules v1.4.3.7-migration-rules-4. Static review has added full Draft 2020-12 validation of each transformed target with a format checker; schema-invalid records are unresolved and withheld from staging. Target digests now use RFC 8785 JCS SHA-256, with a checked-in golden vector. These changes have not been executed in tests or CI.
- Existing unit tests cover unique plan references, started activities, empty legacy lists, missing targets, not-started activities, and duplicate/cross-type IDs. Additional regression cases now cover missing required target fields, invalid nested target objects, and the RFC 8785 digest golden vector, alongside malformed inputs, duplicate typed keys, unmapped statuses, invalid timestamps, type-scoped aliases, empty snapshots, and staging-output safety. They remain unexecuted.
- The integration fixtures include a negative missing-target case and a positive synthetic graph containing one uniquely identified validation plan and one started validation activity.
- The manifest and migration contract both state that the full historical v1.3 machine-readable source bundle is unavailable and compatibility is unverified.
- Target digest contract: RFC 8785 JCS canonical UTF-8 bytes followed by SHA-256; source hashes remain hashes of original bytes. A golden vector is present but unexecuted.
- Schema `$id` policy is documented as a proposal only. The current placeholder host and mixed inherited version labels remain unchanged pending owner approval.
- No transaction commit, active-dataset pointer switch, or rollback implementation exists. The migration report must therefore keep commit_allowed=false.

These tests establish only the declared migration rules on synthetic records. They do not establish compatibility with the complete historical v1.3 schema, all historical record shapes, or a real project dataset.

## Required source input

Provide the exact historical v1.3 baseline used by the project, preferably as one immutable archive containing:

1. the original v1.3 manifest and all record-type schemas;
2. its original fixture index and valid/invalid/conditional fixtures;
3. representative or complete historical JSON/YAML records to be migrated; and
4. any migration notes needed to interpret legacy field semantics.

Record the archive's SHA-256 before inspection. Do not reconstruct the baseline from the v1.4 candidate or silently substitute a later design document.

## Acceptance procedure after the source bundle is available

1. Verify archive integrity and preserve original bytes.
2. Validate the source schemas and fixtures with the source-version validator.
3. Inventory all record types, fields, IDs, project boundaries, and references in the actual source corpus.
4. Run the v1.3-to-v1.4 migration in dry-run mode; classify every field change, quarantined field, collision, and unresolved reference.
5. Resolve validation_ids only from unique same-project source records. A validation activity additionally requires launch evidence; missing or ambiguous targets remain unresolved.
6. Run the full target JSON Schema and cross-record validators against every staged target and the complete staged graph. Full per-record Draft 2020-12 validation is now implemented in the candidate source but has not been executed; cross-record validation and historical compatibility remain separate gates.
7. Repeat the migration with the same source snapshot and rule version; compare canonical target hashes to establish determinism.
8. Publish a source-to-target mapping and a compatibility report. Any unresolved item blocks commit.
9. Keep commit_allowed=false until transaction/rollback safeguards are implemented and the repository owner explicitly authorizes a migration commit.

## Decision boundary

The current source-aware resolver can be reviewed and improved without claiming historical compatibility. Candidate field mappings are listed in `migrations/v1.3-to-v1.4-mapping.json`, but their historical semantics remain unverified until the original v1.3 baseline is supplied. The source archive, full target validation, and transactional migration gates remain mandatory before this item can be marked verified.
